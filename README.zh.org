English README: [[file:README.org][README.org]]

~git-overleaf~ 在项目层级集成 Emacs 与 Overleaf。它会将 Overleaf 项目克隆
为本地 Git 仓库，在仓库中记录 Overleaf 项目元数据，并在本地 Git 历史与
Overleaf 之间同步完整项目快照。

本包面向希望使用本地 LaTeX 编辑、普通 Git 提交和 Git 冲突处理，同时仍需
与使用 Overleaf Web 编辑器的协作者保持同步的用户。

~git-overleaf~ 明确受 [[https://github.com/vale981/overleaf.el][overleaf.el]] 项目启发，并在这一思路上采用项目级
Git 快照工作流。

* 功能

- 将完整 Overleaf 项目克隆为本地 Git 仓库。
- 将已有 Git 仓库绑定到 Overleaf 项目。
- 将本地 Git 快照推送到 Overleaf，并把远端 Overleaf 改动拉回当前分支。
- 通过比较上一次同步的 commit、本地 ~HEAD~ 和最新 Overleaf 快照检测本地
  与远端是否分叉。
- 使用普通 Git 合并工具处理冲突，包括 Magit。
- 在可行时通过 Overleaf 实时文本 OT 通道更新已有文本文档，从而保留远端
  Overleaf 文档 id。
- 将认证 cookies 存入 ~auth-source~、普通 cookie 文件，或仅保存在当前
  Emacs 会话中。
- 可选地在后台 Emacs 线程中执行网络、解压和 Git 操作。
- 为 Overleaf 管理的仓库提供可选的 ~magit-status~ 集成。

~git-overleaf~ 不提供 [[https://github.com/vale981/overleaf.el][overleaf.el]] 的单 buffer 实时编辑工作流。新配置和
既有配置都应直接加载 ~git-overleaf~。

* 需求

~git-overleaf~ 要求 Emacs 29.4 或更新版本，并依赖以下 Elisp 包：

- =websocket= 1.15 或更新版本
- =webdriver= 0.1 或更新版本
- =magit-section= 4.5 或更新版本
- =transient= 0.7.2 或更新版本

项目同步还要求系统中可用以下外部可执行文件：

- =git=
- =curl=
- =unzip=

默认认证后端通过 Selenium webdriver 使用 Firefox，因此需要安装
=geckodriver=。Firefox cookie 导入后端不需要 =geckodriver=，但要求当前
Emacs 构建支持 SQLite。

可选的 =magit-status= 集成在运行时还需要 Magit。

* 安装

** MELPA

~git-overleaf~ 已发布到 MELPA。推荐通过 Emacs 内置包管理器安装。

如果尚未配置 MELPA，请先将它加入 ~package-archives~：

#+begin_src elisp
  (require 'package)
  (add-to-list 'package-archives
               '("melpa" . "https://melpa.org/packages/") t)
  (package-initialize)
#+end_src

然后刷新包列表并安装 ~git-overleaf~：

#+begin_example
M-x package-refresh-contents RET
M-x package-install RET git-overleaf RET
#+end_example

使用 =use-package= 时：

#+begin_src elisp
  (use-package git-overleaf
    :ensure t)
#+end_src

如果使用自建 Overleaf 实例，请在使用交互命令前设置服务器地址：

#+begin_src elisp
  (setopt git-overleaf-url "https://latex.example.edu")
#+end_src

** 开发版安装

如需安装 Git 仓库中的未发布改动，可使用 =use-package= 的 VC 支持：

#+begin_src elisp
  (use-package git-overleaf
    :vc (:url "https://github.com/Jamie-Cui/git-overleaf" :rev "main"))
#+end_src

如果不使用 =use-package=，可直接调用 Emacs 的 VC 包安装器：

#+begin_example
M-x package-vc-install RET https://github.com/Jamie-Cui/git-overleaf.git RET
#+end_example

** 手动 checkout

如果使用本地 checkout，请单独安装 Elisp 依赖，并将本仓库加入
~load-path~：

#+begin_src elisp
  (add-to-list 'load-path "/path/to/git-overleaf")
  (require 'git-overleaf)
#+end_src

包 feature、交互命令和自定义变量均使用 ~git-overleaf-~ 前缀。

* 快速开始

1. 认证 Overleaf：

   #+begin_example
   M-x git-overleaf-authenticate
   #+end_example

2. 克隆 Overleaf 项目：

   #+begin_example
   M-x git-overleaf-clone
   #+end_example

3. 在本地编辑并使用 Git 提交改动。

4. 将本地提交推送到 Overleaf：

   #+begin_example
   M-x git-overleaf-push
   #+end_example

5. 当协作者在 Web 编辑器中修改远端项目后，拉取 Overleaf 改动：

   #+begin_example
   M-x git-overleaf-pull
   #+end_example

如果项目已经存在于本地 Git 仓库中，请运行 ~git-overleaf-init~，而不是
~git-overleaf-clone~，将该仓库绑定到 Overleaf 项目。

* 认证

clone、push 或 pull 前需要有效的 Overleaf 会话 cookies。主要命令为：

#+begin_example
M-x git-overleaf-authenticate
#+end_example

如果 ~git-overleaf-clone~、~git-overleaf-init~、~git-overleaf-fetch~、
~git-overleaf-push~ 或 ~git-overleaf-pull~ 启动时没有有效 cookies，命令会在 minibuffer 中提示
先运行 ~git-overleaf-authenticate~。

** Webdriver 后端

默认后端为 ~webdriver~：

#+begin_src elisp
  (setopt git-overleaf-auth-backend 'webdriver)
#+end_src

它会在空闲本地端口启动 =geckodriver=，打开 Firefox，并要求你登录
Overleaf。即使有旧的 =geckodriver= 进程占用默认端口 =4444=，也不应阻止
重新认证。

默认情况下，认证后的 cookies 会存入 Emacs ~auth-source~。本包会使用
~auth-sources~ 中的第一个文件条目（包括 GPG 加密文件），并在没有可用
条目时回退到 =~/.authinfo.gpg=。更新已有加密文件时会保留原来的加密
收件人。它按 Overleaf host 管理一条记录，并使用 =login git-overleaf=
与 =port git-overleaf-cookie= 进行定位。
重新认证会替换该受管理记录，而不是追加过期副本。

** Firefox cookie 导入

如果 Firefox 已经登录 Overleaf，可以从默认 Firefox profile 导入 cookies：

#+begin_src elisp
  (setopt git-overleaf-auth-backend 'firefox-cookies)
#+end_src

该后端会读取 =profiles.ini=，只导入当前 ~git-overleaf-url~ 对应的
cookies，并在找不到有效 Overleaf session cookie 时给出明确失败信息。它同时
支持旧版 Firefox 使用的秒级过期时间和新版 Firefox 使用的毫秒级过期时间。
如果 Overleaf 拒绝已保存的会话，项目发现会提示重新登录并再次运行
~git-overleaf-authenticate~。若要跳过 profile 自动发现：

#+begin_src elisp
  (setopt git-overleaf-firefox-profile "/path/to/firefox/profile")
#+end_src

** Cookie 存储

使用默认的加密 auth-source 存储：

#+begin_src elisp
  (setopt auth-sources '("~/.authinfo.gpg")
          git-overleaf-cookie-storage 'authinfo)
#+end_src

如果加密文件尚不存在，EasyPG 会在第一次保存时提示选择加密收件人。

将 cookies 存入普通文件：

#+begin_src elisp
  (setopt git-overleaf-cookie-storage "~/.git-overleaf-cookies")
#+end_src

只在当前 Emacs 会话内存中保留 cookies：

#+begin_src elisp
  (setopt git-overleaf-cookie-storage nil)
#+end_src

高级配置可以直接设置 ~git-overleaf-cookies~ 和
~git-overleaf-save-cookies~。

对于 ~git-overleaf-authenticate~ 保存的 cookies，本包会在任何网络请求
前基于本地保存的 session-cookie 过期时间检查会话是否有效。短生命周期的
分析统计类 cookies 不参与该检查。

* 工作流

** 克隆项目

执行：

#+begin_example
M-x git-overleaf-clone
#+end_example

该命令会提示选择 Overleaf 项目，下载完整项目 zip，创建本地 Git 仓库，提
交导入后的快照，并将 Overleaf 元数据写入仓库的本地 Git 配置。

** 绑定已有仓库

在已有 Git 仓库中执行：

#+begin_example
M-x git-overleaf-init
#+end_example

该命令会提示选择远端 Overleaf 项目，将项目元数据写入本地 Git 配置，并初
始化后续 push 和 pull 使用的隐藏 base snapshot。它不会自动从 Overleaf 拉
取，也不会自动推送到 Overleaf。

** 本地编辑

clone 或 init 后，将该仓库作为普通 Git 工作树使用：

- 在本地编辑文件；
- 按需暂存并提交改动；
- 运行 ~git-overleaf-push~ 上传本地提交；
- 运行 ~git-overleaf-pull~ 合入远端 Overleaf 改动。

~git-overleaf-push~ 只上传已经提交的 ~HEAD~。它不会暂存或提交文件，工作树
中的已暂存、未暂存和未跟踪改动都保持不变。命令会获取最新远端快照，并且
只在远端未分叉时上传 ~HEAD~。

与 ~git pull~ 一样，只要 Git 能在不覆盖本地改动的情况下完成合并，
~git-overleaf-pull~ 就允许工作树中存在已暂存、未暂存和未跟踪的改动；
不重叠的改动会保留。如果远端改动会覆盖本地改动，Git 会拒绝合并并原样
保留这些本地改动。pull 仍必须在普通分支上运行，不能处于 detached ~HEAD~
状态。

** 推送到 Overleaf

执行：

#+begin_example
M-x git-overleaf-push
#+end_example

该命令会比较三种状态：

- 上一次成功同步的 Git commit；
- 当前本地 ~HEAD~；
- 从 Overleaf 下载的最新项目快照。

处理规则如下：

| 状态 | 结果 |
|------+------|
| 只有本地发生变化 | 将本地 ~HEAD~ 上传到 Overleaf。 |
| 远端已经与 ~HEAD~ 一致 | 只更新 base ref。 |
| 只有远端发生变化 | 停止并提示运行 ~git-overleaf-pull~。 |
| 本地与远端都发生了不同变化 | 停止并提示先 pull。 |

使用前缀参数 ~C-u M-x git-overleaf-push~ 等价于 ~git push --force~：确认
后用本地 ~HEAD~ 替换发生分叉的远端内容。Lisp API 的第二个参数为 FORCE。

Overleaf 上传由多次 API 修改组成。首次修改远端前，push 会记录恢复 journal。
若上传中断，再次 push 会在远端只是同一目标的部分结果时安全续传；如果
Overleaf 还产生了独立改动，运行 pull 合并，或明确 force-push 覆盖。

对于远端已有的 Overleaf 文本文档，发生变化的 UTF-8 文本会通过 Overleaf 的
实时 ShareJS 文本 OT 路径更新。这样会保留远端文档 id，并在 Overleaf Web
端生成正常的历史记录。更新来源元数据由 Overleaf 实时服务分配，而不是由
客户端提供。发生变化的二进制文件、新增文件、类型冲突和删除条目会使用
Overleaf 上传和删除 API。

如果某个远端文档无法通过当前支持的文本 OT 更新，例如它不是合法 UTF-8、使
用 Overleaf 较新的 ~history-ot~ 类型，或在下载快照后又被远端修改，push 会
失败，而不会静默删除并重建该文档。

** 从 Overleaf 拉取

执行：

#+begin_example
M-x git-overleaf-pull
#+end_example

该命令会比较同样的三种状态。处理规则如下：

| 状态 | 结果 |
|------+------|
| 只有远端发生变化 | 在本地 fast-forward 当前分支。 |
| 本地已经与远端快照一致 | 只更新 base ref。 |
| 远端没有新变化 | 提示当前无需拉取。 |
| 本地与远端都发生了不同变化 | 将远端快照合并到当前分支。 |

如果因远端分叉产生了干净合并，请随后运行 ~git-overleaf-push~，将合并
结果发布回 Overleaf。

pull 会保留与远端传入路径不重叠的本地改动。如果 Git 因本地改动会被覆盖
而拒绝合并，远端快照仍会完成 fetch，但不会记录 pending pull；请先提交、
stash 或移走重叠改动，再重试 pull。

解决 pull 冲突并提交后，普通 push 会完成同步。如果此时 Overleaf 又发生
变化，再次运行 pull 即可；它会继续合并新快照，而不会仅因存在 pending pull
就拒绝操作。

** Reset 到缓存的 Overleaf 快照

执行：

#+begin_example
M-x git-overleaf-fetch
M-x git-overleaf-reset
#+end_example

reset 不访问网络，而是以 ~refs/git-overleaf/remote~ 中已经缓存的快照为
目标。无前缀时采用 mixed reset 语义：移动 HEAD 并重置索引，但保留工作树
文件。~C-u M-x git-overleaf-reset~ 采用 hard reset 语义，同时替换已跟踪的
工作树文件。两种模式都保留未跟踪和忽略文件，命令永远不会运行 ~git clean~。
移动 HEAD 前会创建安全 ref；成功后更新 base 并清除 pending 同步元数据。

** Force-push 到 Overleaf

执行：

#+begin_example
C-u M-x git-overleaf-push
#+end_example

force push 使用同一条只上传 HEAD 的路径，但会有意替换发生分叉的远端内容。
存在活动或未解决的 Git merge 时它会拒绝执行。成功后会清除原 pending 同步
状态；如果中途失败，则保留可续传的 push journal。

** 冲突处理

当本地与远端快照分叉时，先运行 ~git-overleaf-pull~。该命令会使用普通
Git 合并机制，将下载下来的远端快照合并到当前分支。

如果合并产生冲突：

- 当前分支会保持在 Git 的标准冲突合并状态；
- 使用 Magit 或普通 Git 解决冲突；
- 创建 merge commit；
- 运行 ~git-overleaf-push~ 上传合并结果。

要放弃活动的 pull，运行 ~git-overleaf-pull-abort~。它执行
~git merge --abort~，并且只在 Git 成功后清除 pending 元数据。如果 merge
已经手动中止，它只清除过期元数据。merge 已提交后它会拒绝执行，因为静默
改写已提交历史并不安全。

中止后，可以 force push 保留本地内容；也可以用 ~git-overleaf-reset~ 接受
缓存的远端快照（前缀参数选择 hard 模式）。

冲突处理有意交给 Git，而不是 ediff。

* 同步细节

clone、init、push 和 pull 命令会将项目元数据存入仓库的本地 Git 配置。仓
库绑定后，可以从该仓库内任意目录继续运行 push 和 pull。

clone 和 init 可以注册名为 =overleaf= 的无分支逻辑 Git remote。它没有 URL、
push URL 或 refspec；其本地标记让 Magit 在普通 remote 选择中把该名字转交给
git-overleaf。逻辑 remote 是可选的：所有 git-overleaf 命令以及显式 Magit
=O= 动作都不依赖它。只有需要这种路由时才运行 ~git-overleaf-register-remote~。

最近一次成功观察到的远端快照保存在 ~refs/git-overleaf/remote~，与记录同步
基线的 ~refs/git-overleaf/base~ 相互独立。=origin= 等普通 remote 不受影响。

当 ~git-overleaf-sync-metadata-enabled~ 为非 nil 时，成功的 push 操作
会在 Overleaf 项目根目录维护 ~.git-overleaf-sync.json~。该文件记录本
包上次上传的本地 Git commit 和 tree。下载快照后，它会在 Git 比较前被移
除，因此它是同步 bookkeeping，而不是普通项目内容。它不应被本地 Git 仓库
跟踪。

在可能移动当前分支或完成 pending sync 状态的同步步骤前，如果
~git-overleaf-local-backups-enabled~ 为非 nil，本包会在
~refs/git-overleaf/backups/~ 下创建本地安全 refs。这些 refs 会让之前
的本地 commit 在分支移动和 reflog 过期之外仍然可达。

查看 backup refs：

#+begin_example
git show-ref refs/git-overleaf/backups
#+end_example

从 backup ref 创建普通分支以恢复：

#+begin_example
git branch recover-overleaf refs/git-overleaf/backups/...
#+end_example

空目录不会被 Git 跟踪，因此 push 或 pull 时也不会被保留。

* 异步操作

默认情况下，命令同步运行。若希望在耗时网络、解压和 Git 工作期间保持
Emacs 响应：

#+begin_src elisp
  (setopt git-overleaf-enable-async t)
#+end_src

交互命令仍会在前台收集 minibuffer 输入和确认，随后在后台执行耗时工作。
这适用于 clone、init、fetch、push、pull、认证和 Magit 远端刷新。status、
reset 与 pull-abort 都是本地操作。

取消当前所有已跟踪的 Overleaf 后台操作：

#+begin_example
M-x git-overleaf-force-stop
#+end_example

取消会尽可能中断外部进程、清理 async 锁，并丢弃尚未执行的前台回调。已
经在本地或远端完成的工作不会自动回滚。

* 下载与上传进度

快照下载会在 ~git-overleaf-log-echo~ 为非 nil 时，在 minibuffer 中显示
=Downloading project ... N%= 形式的 curl 进度。

push 会用 =Uploading content for project ... N% (I/T: ACTION PATH)=
显示已完成的内容变更操作数和当前路径。这是操作级而不是字节级进度，因为一次 push
可能混合文本 OT 更新、multipart 上传、创建目录和删除操作。因此单个较慢的
远端请求完成前，百分比可能暂时不变。内容达到 100% 后，会用另一条提示标明
sync metadata 正在收尾。进度提示是临时的，不会写入项目日志或 =*Messages*=。

** 代理环境

下载由 ~git-overleaf-curl-executable~ 指定的 curl 执行，因此代理配置来自
Emacs 的 ~process-environment~，不一定等同于运行 =emacsclient= 的 shell。
如果 GUI Emacs 中下载 Overleaf 很慢，先在 Emacs 里检查
=(getenv "HTTPS_PROXY")= 和 =(getenv "HTTP_PROXY")=，再按需用 =setenv= 或
=exec-path-from-shell= 之类的工具把代理变量复制进 Emacs。

* Magit 集成

若要在 =magit-status= 中显示 Overleaf section，请加载可选集成：

#+begin_src elisp
  (with-eval-after-load 'magit
    (require 'git-overleaf-magit)
    (git-overleaf-magit-setup))
#+end_src

对于 Overleaf 管理的仓库，该 section 会始终显示，并区分远端未检查、正在
刷新、已同步、仅本地变化、仅远端变化和双方都有变化。标题也会提示 staged、
unstaged、untracked 或 unmerged 工作区变化；具体工作区 diff 仍由 Magit 的
标准 section 展示。本地和远端快照 diff 默认折叠，只在展开时生成。

每次 =magit-status= 刷新也可能在后台刷新远端 Overleaf 快照。这个 Magit 专用
后台刷新由 ~git-overleaf-magit-auto-refresh-remote~ 独立控制，不再依赖
~git-overleaf-enable-async~。自动刷新会被内部节流，并与 push/pull 共用仓库
操作锁，因此普通 Magit 刷新既不会阻塞，也不会与正在执行的同步操作竞争。

若要保持手动远端刷新：

#+begin_src elisp
  (setopt git-overleaf-magit-auto-refresh-remote nil)
#+end_src

仍可手动刷新远端状态：

#+begin_example
M-x git-overleaf-magit-refresh-remote
#+end_example

Magit 的 fetch、pull 和 push transient 都会增加一个大写 =O= 动作。这些显式
动作不依赖逻辑 remote。fetch 只更新 ~refs/git-overleaf/remote~；=-f=/
=--force= 不会把 fetch 变成 reset。pull 调用 ~git-overleaf-pull~。push 调用
~git-overleaf-push~；Magit 的 force 选项会给同一个命令传入前缀并请求确认，
=--force-with-lease= 则保持普通受保护 push。其他 Git 专用参数会被拒绝。

注册逻辑 remote 后，从 Magit 普通 fetch 动作选择它会把快照刷新转交给
git-overleaf；不支持分支和 refspec。其他 Git remote 保持 Magit 原始行为。
显式 =O= fetch 不受自动刷新节流限制。

在 Overleaf section 上，=G= 刷新远端，=RET= 在浏览器中打开项目。
=C-c C-c= 是命令前缀，包含：

| 按键 | 命令 |
|------+------|
| =b= | 浏览 Overleaf 项目。 |
| =f= | 获取远端快照。 |
| =g= | 刷新远端快照。 |
| =l= | 从 Overleaf 拉取。 |
| =p= | 推送到 Overleaf。 |
| =q= | 中止 pending pull。 |
| =R= | Reset 到缓存的远端快照。 |
| =r= | 注册逻辑 Overleaf remote。 |
| =s= | 显示缓存的同步状态。 |
| =L= | 显示 git-overleaf 日志。 |
| =k= | 停止后台 Overleaf 操作。 |

* Commit Hook

若要在 Emacs 中通过 Magit 或 =git-commit= 创建 commit 后自动 push：

#+begin_src elisp
  (with-eval-after-load 'git-commit
    (add-hook 'git-commit-post-finish-hook
              (lambda () (git-overleaf-push nil nil t))))
#+end_src

该 hook 只会 push 已经包含 Overleaf 项目元数据的仓库。命令同步运行时，该
hook 会在 push 运行期间阻塞 Emacs。启用 ~git-overleaf-enable-async~
可让 hook 触发的 push 在后台运行。

* 日志

Overleaf 信息、警告和 debug 条目写入全局
~*git-overleaf-log*~ buffer。每条记录都包含时间戳、日志级别，以及当前
可获得的项目、仓库或 Overleaf URL 上下文，便于区分多个项目的日志。

启用详细 debug 日志：

#+begin_src elisp
  (setopt git-overleaf-debug t)
#+end_src

* 安全说明

Overleaf cookies 可以访问你的 Overleaf 账户。请保护 auth-source 文件和自
定义 cookie 文件，不要提交真实 cookies、项目标识符、ancestor backup 文
件，或包含会话数据的 debug 日志。

* 开发

仓库包含一个简单的 =Makefile= 用于本地验证：

#+begin_example
make
make test
make coverage
make help
make clean
#+end_example

如果 Emacs 可执行文件在 =PATH= 中不是 =emacs=：

#+begin_example
make EMACS=/path/to/Emacs
#+end_example

等价的 batch 验证命令：

#+begin_example
emacs -Q --batch -L . --eval "(progn (require 'package) (package-initialize))" -f batch-byte-compile git-overleaf.el
emacs -Q --batch -L . --eval "(progn (require 'package) (package-initialize))" --eval "(require 'git-overleaf)"
#+end_example

自动化测试套件使用 ERT，并设计为可离线运行：

#+begin_example
make test
#+end_example

它覆盖纯 helper、cookie 和 HTTP 边界逻辑、本地 Git 快照与状态流转、使用
stub Overleaf API 的远端树 diff、命令分发、async 状态处理，以及少量
Magit 集成 helper。它有意不连接 Overleaf、不启动 webdriver，也不打开浏览
器。

对于影响真实服务边界的改动，仍应使用真实 Overleaf 会话验证 clone、init、
push、pull、pending-state recovery 和 Git 冲突处理。对于认证相关改动，请
尽可能验证 webdriver 认证和 Firefox cookie 导入。

当前默认构建不会自动运行覆盖率统计，但仓库提供基于 Emacs 内置
=testcover= 的可选目标：

#+begin_example
make coverage
make coverage COVERAGE_MIN=50
#+end_example

该目标会将 tab 分隔的摘要写入 =coverage/testcover-summary.tsv=。可选的
=COVERAGE_MIN= 变量会把报告变成阈值检查。GitHub Actions 也提供手动
=workflow_dispatch= 触发入口，会运行 =make coverage= 并上传摘要 artifact。
外部包 =undercover.el= 也可以把 ERT 覆盖率上报到托管覆盖率服务，但这不属
于默认 CI 路径。
